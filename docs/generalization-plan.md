# Generalization plan and limits

H5Reclaim's long-term goal is to recover measurements that remain physically present in damaged HDF5 storage, place them only where the surviving evidence justifies, and identify everything else as unknown. This document is a development plan, not a list of implemented recovery capabilities. The [current status](status.md) and [usage guide](usage.md) describe the running release.

## What is supported today

The recovery command selects one local chunked dataset, usually using native metadata. A bounded raw fallback can resolve an old symbol-table or modern compact-group hard-link path when native open fails on damaged auxiliary metadata. The older version-1 raw-data B-tree route traverses intact deeper trees and can bridge at most one missing **leaf** link through a unique two-sided reciprocal sibling bridge and matching parent interval. The newer route validates checksummed superblock/object headers, layouts 4/5, and intact single-chunk, implicit, fixed-array, extensible-array, or version-2 B-tree indexes. Fixed arrays include filtered, paged and sparse slots; EA pages are still refused. Structural datasets accept rank one through four canonical fixed-width integers and IEEE float32/64 in either byte order, bounded built-in filters in declared order, edge chunks, growth, and sparse unknown cells. Every accepted region is reconciled in an evidence ledger and exported to a new file with a status map. The separate `export-readable` command uses a bounded child worker for currently native-readable fixed-size local schemas; it cannot repair an inaccessible index or establish historical truth.

Four unchanged scientific files are bundled for surveying; six of their 251 inventoried datasets currently fit the metadata preflight rules. All six have been separately checked against the originals on intact copies; the controlled 16 kHz GWOSC trial tests one broken index pointer. The original healthy file is used to generate and independently score controlled experiments; recovery receives only the damaged file. These experiments do not measure coverage of unrelated failures. The [HDF5 format specification](https://support.hdfgroup.org/documentation/hdf5/latest/_f_m_t4.html) defines additional structures and limits.

## Two independent questions

**Format support** asks whether the engine can interpret the file's superblock, object headers, datatype, layout, index, and filters. **Damage recoverability** asks whether enough correct bytes and anchors survived to establish the measurements' original values and positions. Supporting a format does not imply that every damaged instance can be recovered. Conversely, a partially broken file that cannot be opened by the standard library might still contain recoverable bytes if the engine can establish their meaning through surviving evidence.

The HDF5 [dataset storage guide](https://support.hdfgroup.org/documentation/hdf5/latest/_l_b_dset_layout.html) describes compact, contiguous, and chunked storage. Chunked datasets have no single universal index: older layouts use version-1 B-trees; newer layouts can use single-chunk, implicit, fixed-array, extensible-array, or version-2 B-tree indexes. Index choice depends in part on allocation and whether dimensions can grow. Superblock versions 0 through 3, object-header versions 1 and 2, and data-layout versions also differ. Layout version 5 changes filtered chunk-record encoding. The version number and actual messages, not a filename extension or scientific field, must select the parser.

| Storage or index | Structural reconstruction in this release | Proposed recovery evidence and first safe case |
| --- | --- | --- |
| Compact | Unsupported for raw structural recovery; readable numeric data can be copied through native HDF5 | Intact, independently identified object header containing both layout and payload; preserve exact datatype and dataspace. Header destruction may erase the payload itself. |
| Contiguous | Unsupported for raw structural recovery; readable allocated numeric data can be copied through native HDF5 | Intact layout's raw-data address and dataspace, bounded physical extent, canonical datatype; identify corruption within the extent separately. |
| Version-1 chunk B-tree | Intact level-zero or deeper root; one uniquely bridged missing leaf link | Multiple detached nodes or a missing internal subtree need independent attribution; require parent bounds, ownership, uniqueness, and non-overlap. |
| Single-chunk and implicit index | Intact version-4/5 selected layout, raw address and coordinate validated | Missing direct base addresses and broken modern metadata are not reconstructed. Other schemas still require independent support. |
| Fixed-array index | Intact filtered, paged, sparse blocks with checked FAHD/FADB headers, bitmap/page checksums and row-major slots; generated differential fixtures | Broken header/page links and unanchored orphan pages remain unassigned. |
| Extensible-array index | Intact EAHD/EAIB/EASB/EADB pointer chains, filtered slots and sparse growth within bounds | Paged EA data blocks and lost parent links still need an independently checked strategy. |
| Version-2 chunk B-tree | Intact checksummed BTHD/BTIN/BTLF, filtered records, deep tree traversal and sparse coordinates | Broken tree links, ambiguous detached nodes, and historical stale records remain unresolved. |
| External storage and virtual datasets | Declared-name inventory and explicit hash-pinned file-set validation; **no dependent-value export** | Snapshot all supplied sources together and prove source mappings/coverage before any values can be accepted. Missing external bytes cannot be obtained from an HDF5 container that does not store them. |

This is a map of possible engineering work, not a promise that each damaged case has sufficient evidence. Appendix C of the official [file-format specification](https://support.hdfgroup.org/documentation/hdf5/latest/_f_m_t4.html) documents all five newer chunk indexes, while HDF5's [external-storage property](https://support.hdfgroup.org/documentation/hdf5/latest/group___d_c_p_l.html) and [virtual dataset feature](https://support.hdfgroup.org/documentation/hdf5/latest/rel_spec_110.html) show why some datasets depend on other files.

## Proposed engine boundaries

1. **Acquire immutable evidence.** The current route streams a stable snapshot of the primary input, records its size/hash, and rejects source changes. Related files are separately hash-validated for diagnosis; an atomic, jointly captured dependency set is future work. Never alter source bytes. Put reads, traversal, allocations, decompression, and elapsed work under documented limits; larger opt-in limits must not remove bounds.
2. **Inspect before deciding a path.** Try the HDF5 library for metadata and intact values where it can safely open the snapshot. Independently parse only documented on-disk variants needed for damaged metadata. Keep parser implementations keyed by actual signature, version, layout class, and index type. A raw signature scan produces *candidates*, not accepted datasets.
3. **Record candidate provenance.** Carry dataset identity, proposed coordinates, source file and byte extent, raw index record, parent and sibling relationships, allocation state, filter mask, and every check performed. A missing address or broken path must never be filled by a plausible shape alone. A detached block can belong to another dataset or to freed/stale storage.
4. **Reconcile ownership and integrity.** Resolve a candidate only when its dataset attribution and coordinate are unique under the available structural evidence. Check bounds, non-overlap with parsed metadata and accepted payloads, datatype size, filter pipeline, chunk edge rules, and contradictory records. Apply supported filters in reverse declared order with each chunk's skip mask and strict expansion limits. Keep raw undecoded bytes as separate evidence if a filter is missing; do not assign decoded measurements. A filter checksum tests certain byte errors, but does not prove historical authenticity.
5. **Export uncertainty with the data.** The output includes a validity/status map, detailed ledger, and readable summary. A separate bounded raw-fragment ZIP can hold anchored undecodable extents without assigning coordinates; it cannot conjure unknown extents. Distinguish checksum-verified payload, structurally placed payload without an independent checksum, ambiguous candidate, decode failure, unsupported case, and unavailable region. Preserve source schema and scientific context only where specifically implemented and verified. Never let a fill value alone signal missing measurements. Failed or incomplete publication must not look like completed recovery.

The [HDF5 filter guide](https://support.hdfgroup.org/documentation/hdf5/latest/_h5_z__u_g.html) lists DEFLATE, SZIP, shuffle, Fletcher32, NBIT, lossy scale-offset, and custom filters. Their sequence and per-chunk skip masks affect decoding. Unknown plugins, particularly executable third-party filters, must not be loaded automatically. The [dataset APIs](https://support.hdfgroup.org/documentation/hdf5/latest/group___h5_d.html) can enumerate chunk coordinates, physical addresses, sizes, and masks for intact indexes; those observations are useful cross-checks on controlled healthy references, not substitutes for damaged-index reasoning.

## Scientist input when the file cannot explain itself

Auto-inspection should ask for help only where evidence is insufficient. A guided case form can accept optional dataset path, expected shape and axis order, element type and byte order, chunk shape, filter IDs/settings, acquisition software/version, instrument run logs, collection of related files, and independently recorded checksums or sample hashes. It should show which facts were read from the damaged file, which came from a scientist, and which are merely inferred.

A hint narrows a search but is not proof. For example, knowing that an experiment stored `(time, channel)` `float64` samples does not identify which surviving compressed block belongs to a given time interval. If two assignments satisfy the same hints, mark both ambiguous. Where sufficient anchors are missing, offer a separately labeled raw-fragment export for expert analysis; do not put those fragments in scientific coordinates or silently convert them into the existing supported schema. A scientist should not have to know HDF5 internal index types to start an inspection.

## Milestones and exit gates

| Phase | Deliverable | Required evidence before calling it supported |
| --- | --- | --- |
| 1. Triage and evidence model | Typed ledger, active v1/modern adapters, hints, status/dependency diagnosis, fragment export implemented | Expand parser trust-boundary fuzzing and contradictory multi-dataset cases; never accept from scan or hint alone. |
| 2. Broaden older formats | Deeper version-1 trees, edge chunks and fixed-width numeric schemas implemented; compact/contiguous raw paths remain | Differential checks against independent truth and adversarial stale structures are needed before each new variant. |
| 3. Newer metadata/indexes | Five modern index families implemented within bounded variants; compact-group fallback, filtered/paged fixed arrays, and deep version-2 tree tests | Dense groups, paged EA, broken modern links, and naturally damaged cases require new ownership evidence. |
| 4. Filters and dependencies | Bounded filter registry, variable filter masks, file-set handling for external/VDS | Known-answer decoding for each pipeline and skipped-filter combination, missing-plugin/dependency refusal, no implicit executable plugin loading. |
| 5. Field validation | Consented naturally damaged cases, independent review and cross-tool comparison | Audited provenance, exact truth where available, uncertainty where unavailable, publishable denominator and false-accept measurement. |

These phases can overlap when a real user case establishes a better priority. An intact level-zero export of the bundled 4 kHz GWOSC dataset is a first phase-2 increment; a broken payload pointer in that direct index still has no justified reconstruction strategy. A new parser or decoder passes only when positive and deliberately misleading negative cases succeed. The library's [`h5clear` utility](https://support.hdfgroup.org/documentation/hdf5/latest/_h5_t_o_o_l__c_r__u_g.html) handles some file status or end-of-address situations, but the HDF Group explicitly says it is not a general corruption-repair tool; diagnosis should distinguish these simpler cases from lost data structures.

## Measuring coverage honestly

Maintain a pinned corpus of unchanged files from different scientific producers, versions, storage layouts, datatypes, filters, and dimensions. Inventory both supported and unsupported datasets. In a separate test workspace, inject documented faults into copies: bit flips and burst writes in headers/indexes/payloads, invalid addresses, broken links, partial truncation, inconsistent checksums, interrupted-write state, stale/deallocated candidate structures, missing external files, and combinations. Randomize positions and magnitudes **within each fault class** with published seeds and mutation manifests. Do not choose only faults the implementation was designed to repair. Add held-out cases and naturally damaged files where owners permit analysis; a naturally damaged file without trustworthy reference cannot support an exact-value success claim.

Report at least: format support by stratum, recoverable-byte fraction, recovered correct coordinates and exact values, unresolved regions, falsely accepted coordinates or wrong values, outright refusal, time and memory limits, source preservation, and regression across versions. Distinguish a structurally valid export from an independently verified original measurement. Compare with documented existing approaches on the same cases when possible. A corpus of healthy datasets, or hundreds of mutations of one pointer pattern, does not measure general recovery coverage.

**“99%” needs a defined denominator.** It could mean supported files in a declared population, recoverable chunks under a stated fault distribution, or exact values from cases with independent truth; these are different claims. Publish the target population, inclusion criteria, fault distribution, sampling process, confidence interval, exactness threshold, unsupported/refused cases, and wrong-data rate. Require held-out independent evaluation and important strata rather than extrapolating from a single aggregate score. No current result supports any claim that H5Reclaim handles 99% of HDF5 damage causes.

## Irrecoverable and fundamentally uncertain cases

If the only copy of payload bytes was erased or overwritten, the original value cannot be deduced without independent redundancy, a separate copy, or domain-specific external evidence. If an index and all corroborating coordinate/ownership metadata were lost, surviving bytes can admit multiple equally valid assignments. A compressed block can remain decodable while its old location is unknowable. Damaged datatype or filter descriptions may make the same bytes represent several different datasets. Checksums detect some damage; they do not reconstruct the bytes they reject and cannot guarantee an unmodified scientific value. Lossy filters already discard information by design.

Failure can also occur outside the main file: [external raw storage](https://support.hdfgroup.org/documentation/hdf5/latest/group___d_c_p_l.html) and [virtual datasets](https://support.hdfgroup.org/documentation/hdf5/latest/rel_spec_110.html) reference other files. User context may help identify these files, but cannot recreate missing measurements. In each of these cases, a careful refusal, partial output with a validity mask, or unassigned forensic fragment is a correct outcome. Universal exact repair of arbitrary damaged HDF5 files is not achievable from the damaged file alone.
